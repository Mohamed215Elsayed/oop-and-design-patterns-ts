# O — Open-Closed Principle (OCP)

## المبدأ
الـ **class** لازم يكون:
- **Open** للتوسع (extension) — تقدر تضيف عليه سلوك جديد وقت ما تحتاج.
- **Closed** للتعديل (modification) — من غير ما تحتاج تلمس أو تعدّل الكود الأساسي (code base) الموجود بالفعل.

الهدف الأساسي: **منع أي خطأ غير متوقع** بسبب التعديل في class مستخدم بالفعل في أكتر من مكان (زي الـ classes الموجودة جوه الـ frameworks). فبدل ما تعدّل الكود الأصلي، تضيف السلوك الجديد من خلال **subclass** أو **abstraction** جديدة.

> **ملاحظة مهمة:** المبدأ ده **مش بينطبق على الـ bugs**. أي bug لازم يتصلح جوه الـ class نفسها مباشرة، ومينفعش تسيبه يتوارث لأي subclass جديد.

أكتر وقت بيتطبق فيه المبدأ ده هو لما الـ class بيتم تصديره للاستخدام الفعلي (production) ومشاركته مع فرق تانية أو third parties — عشان تضمن إن الكود الحالي مش هيتعطل، وفي نفس الوقت يفضل قابل للتطوير.

## المثال (من الشرح)
عندنا `Order` class فيه method `getShippingCost()` بتحسب تكلفة الشحن حسب نوعه (`ground`, `air`...).

## المشكلة (`bad-example.ts`)
منطق حساب تكلفة كل نوع شحن **مكتوب مباشرة (hard-coded)** جوه `Order` class على شكل سلسلة `if/else`. أي تعديل مباشر — زي إضافة نوع شحن جديد (`sea` مثلاً) — هيضطرك **تعدّل جوه `Order` نفسها** وتضيف `break` جديد في السلسلة، وده مخالف تمامًا لمبدأ "Closed for modification"، وبيخلي الكود عرضة للأخطاء كل مرة نضيف فيها نوع جديد.

## الحل (`good-example.ts`)
1. بننشئ **interface** اسمها `Shipping` فيها الـ methods المشتركة (`getCost`, `getDate`).
2. كل نوع شحن (`Ground`, `Air`...) بيعمل implement للـ interface دي في class مستقل.
3. `Order` بقت بس بتحتفظ بـ instance من `Shipping` (composition)، وبتنادي `shipping.getCost(this)` من غير ما تعرف تفاصيل كل نوع شحن.

**النتيجة:** إضافة نوع شحن جديد (زي `Sea`) هتحتاج بس class جديد يعمل implement لـ `Shipping`، **من غير أي تعديل في `Order`** أو أي class موجود بالفعل.

## الفايدة
- إضافة سلوك جديد (extension) من غير خطر كسر كود شغال بالفعل.
- تقليل احتمالية الأخطاء غير المتوقعة في الكود المستخدم في أكتر من مكان.
- الكود بيصبح أكتر قابلية للتوسع بشكل ممتاز مع أي إضافة مستقبلية.
